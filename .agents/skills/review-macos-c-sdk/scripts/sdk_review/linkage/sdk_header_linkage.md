# Which library supplies an SDK C declaration?

Run this reference audit when investigating an undefined symbol or deciding whether a header belongs in the libSystem qualification profile. Keep its generated files local. They contain metadata read from the official SDK.

## Reproduce the assessment

```sh
python3 -m sdk_review.linkage.sdk_header_link_candidates --sdk "$APPLE_SDK" --llvm "$LLVM" \
  --out "$WORK/candidates.json"
python3 -m sdk_review.linkage.classify_sdk_header_links bindings --sdk "$APPLE_SDK" --llvm "$LLVM" \
  --candidates "$WORK/candidates.json" --out "$WORK/bindings.json" --names-out "$WORK/names.txt"
python3 -m sdk_review.linkage.lookup_tbd_symbols --sdk "$APPLE_SDK" --llvm "$LLVM" \
  --symbols-file "$WORK/names.txt" --raw-symbol _profil --raw-symbol _add_profil \
  --raw-symbol _unwhiteout --raw-symbol _zlibVersion --out "$WORK/providers.json"
python3 -m sdk_review.linkage.classify_sdk_header_links join --bindings "$WORK/bindings.json" \
  --providers "$WORK/providers.json" --c-install "$C_INSTALL" --out "$WORK/assessment.json"
```

The first pass tries each logical C header individually under `usr/include`, excluding the C++ tree and headers that resolve into frameworks. The second makes actual LLD links at the scanner's deployment minimum. Each `-u` asks for one Mach-O name; `-undefined dynamic_lookup` lets the audit distinguish thousands of unresolved names in a single set of links. Only a two-level import through libSystem counts as a libSystem binding. A symbol that has no observable named import remains a separate investigation. No client generated by this diagnostic is shipped.

The third pass searches SDK-wide, including stubs inside public and private frameworks, aliases, embedded libraries, explicit forwarded symbols, reexports and linker directives. The last pass reports other candidate providers per header. For arm64 it includes raw arm64 and arm64e matches as leads. Confirm the owner and the library the client binds through with an ordinary strict link. Account for a library's allowed clients and its umbrella. A spelling match with a private framework is insufficient to approve an API.

## SDK 26.5 build 25F70

All 3,259 physical TBDs parsed, containing 3,520 primary and embedded documents. There were 2,839 TBD symlink aliases. No document named `_profil`, `_add_profil` or `_unwhiteout` as an export, reexport or linker-directive subject. The independent raw text check also found no matching tokens. Both targets failed strict links at minima 11.0 and 26.5.

The declarations are present in Apple's pinned Libc source. Its public install script processes `include/unistd.h`; the resulting 26.5 file is byte-identical to the reference SDK header. Corentin approved retaining all three declarations and omitting exactly their linker exports from the 26.5 stub. Apple's profiling implementation explains that the underlying `profil` and `add_profil` syscalls had been unsupported since 2008. The evidence for `unwhiteout` establishes its declaration and lack of a shipping link provider. [Apple's declarations](https://github.com/apple-oss-distributions/Libc/blob/4e34d0559e3a1b081afeb8604d9e204a1f31321d/include/unistd.h#L819-L920) · [Apple's install rule](https://github.com/apple-oss-distributions/Libc/blob/4e34d0559e3a1b081afeb8604d9e204a1f31321d/xcodescripts/headers.sh#L144) · [Profiling history](https://github.com/apple-oss-distributions/Libc/blob/4e34d0559e3a1b081afeb8604d9e204a1f31321d/gmon/gmon.c#L80-L85) · [Expected undefined policy](data/macosx26.5/expected-undefined.json)

The scan attempted 1,699 logical header paths for each target at minimum 11.0. On each architecture, 559 headers yielded external names. Direct parse failures numbered 399 on arm64 and 404 on Intel. The remaining 741 and 736 direct contexts yielded zero external names. Conditional APIs, include prerequisites, macros and inline-only calls can add demands when a consumer uses the header.

The last two are `___dso_handle` and `__mh_dylib_header`. A separate strict link with actual relocations and no libraries resolved both locally on each architecture. Neither needs a TBD provider. The raw candidate count includes alternate build variants such as the introspection libdispatch and libraries with restricted clients.

272 arm64 and 271 Intel reference header paths had at least one candidate supplied elsewhere. Six paths also existed in our 767-header installation. Strict links of actual C references compiled against **our installation** confirmed these examples on both targets.

The DriverKit result establishes a link against this SDK. It does not establish ordinary macOS application support. Other verified SDK-only examples include `sqlite3.h` (`-lsqlite3`), `resolv.h` (`-lresolv`), `compression.h` (`-lcompression`), `libxml/parser.h` (`-lxml2`), curses, Expat, bzip2, editline, xar and curl. In contrast, clients for `sin` and `pthread_create` already bind through libSystem, including when they pass `-lm` or `-lpthread`.

Exercise BSM with an arm64 C object that references the declared function.
Link once with `-lSystem` alone to observe the missing export, then add the library.

```sh
ARCH=arm64
printf '%s\n' '#include <sys/types.h>' '#include <bsm/audit_record.h>' \
  '__typeof__(&au_bsm_to_errno) demand = &au_bsm_to_errno;' |
  "$LLVM/bin/clang" --no-default-config -target "$ARCH-apple-macos11" -x c -c - \
    -nostdinc -isysroot "$C_INSTALL" -isystem "$("$LLVM/bin/clang" -print-resource-dir)/include" \
    -isystem "$C_INSTALL/usr/include" -o "$WORK/bsm-$ARCH.o"
"$LLVM/bin/ld64.lld" -dylib -arch "$ARCH" -platform_version macos 11 26.5 \
  -Z -syslibroot "$APPLE_SDK" -L"$APPLE_SDK/usr/lib" "$WORK/bsm-$ARCH.o" \
  -lSystem -lbsm -o "$WORK/bsm-$ARCH.dylib"
"$LLVM/bin/llvm-nm" -um "$WORK/bsm-$ARCH.dylib"
```

The supported classification distinguishes a libSystem binding, a separately qualified dylib or framework binding, a toolchain/linker-provided symbol, an evidenced declaration without an SDK link provider, and an unresolved investigation. Review non-libSystem matches before promoting provider facts into a production lock. An approved missing libSystem export and a missing SDK-wide provider have different consequences for consumers.

## Packaging decision for zlib

The standalone C package may omit both `zlib.h` and `zconf.h`. A Bazel consumer using zlib should declare a zlib dependency that supplies its headers and link input. Our libSystem package has no obligation to ship a libz stub or satisfy zlib symbols. The SDK discovery probe can still inventory Apple's zlib for comparison. The current header recipe and shipping probe still include it. This decision applies only to zlib. The packaging decision for iconv remains open.
